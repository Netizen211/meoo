  [FATAL-1] getOrderRefundAmount 危险回退逻辑 (行51-55)
    描述: 当订单数据中不存在退款金额字段时，函数回退到用户实付金额作为退款金额，
          导致无售后的正常订单也被计入退款，退款总额严重虚高。
    代码:
      function getOrderRefundAmount(order: any): number {
        const explicitRefund = safeFloat(findField(order, '买家退款金额', '退款金额', ...));
        if (explicitRefund > 0) return explicitRefund;
        return safeFloat(findField(order, '用户实付金额(元)', '用户实付金额', ...)); // ← 危险回退
      }
    影响: 退款率KPI、退款金额KPI、退款明细全部虚高，与AfterSalePage共享同一bug。
    修复: 找不到退款字段时返回0，永不回退到用户实付金额。

  [FATAL-2] promoKpi 零值假值bug (行321-322)
    描述: 使用 `||` 运算符导致值为0的字段被跳过，fall through到备选字段。
    代码:
      totalCost += safeFloat(r['总花费(元)'] || r['花费(元)'] || r['成交花费(元)']);
      promoGMV += safeFloat(r['交易额(元)'] || r['成交金额(元)']);
    影响: 当某条推广记录的"总花费(元)"字段值为0时（而非不存在），
          safeFloat(0)=0 为假值，|| 运算符导致回退到"花费(元)"字段，
          造成花费数据重复累加。
    修复: 先判断字段是否存在（findField），存在则用其值（包括0），不存在才回退。
    关联: 与 PromotionPage 审计报告中的 FATAL-2 完全相同的根因。

  [FATAL-3] findField 第6份独立拷贝 (行16-31)
    描述: 与 UploadPage/AfterSalePage/InsurancePage/LogisticsPage/CostManagementPage
          中的 findField 实现完全相同，是项目中第6份拷贝。
    影响: 任何bug修复需要在6个文件中同步修改。
    修复: 提取到 src/utils/fieldAccess.ts 统一维护。

  [FATAL-4] 25个KPI全部基于订单CSV计算，无独立数据源合并
    描述: 所有KPI（包括售后率、退款率、推广ROI等）仅从 orders 数组计算。
          当用户只上传售后Excel或推广Excel（不含订单CSV）时，
          售后KPI和推广KPI全部为0或null。
    影响: 仅上传售后/推广数据的场景下，Dashboard核心指标大面积缺失。
    关联: 与 AfterSalePage FATAL-5（双数据源设计缺陷）同根因。

  [SEVERE-1] 25个KPI fmt函数不一致
    描述: 部分KPI使用 toFixed(0)，部分使用 toLocaleString()，格式不统一。
    代码位置: 行82-308 (kpiCards数组)
    示例:
      fmt: (v: number) => `¥${v.toFixed(0)}`       // GMV类
      fmt: (v: number) => `¥${v.toLocaleString()}`  // 利润类
      fmt: (v: number) => `${v.toFixed(2)}`         // ROI类

  [SEVERE-3] 利润计算使用 evaluateFormula，但缺少公式校验
