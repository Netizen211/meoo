# Karpathy 编码指南（12 条完整版）

源自 [Andrej Karpathy 对 LLM 编码陷阱的观察](https://x.com/karpathy/status/2015883857489522876)，原始 4 条由 Forrest Chang 整理（[forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills)），扩展 8 条来自 [@Mnilax](https://x.com/Mnimiy) 在 30 个代码库 6 周实测。

**实测数据：** 无规则 41% 错误率 → 4 条 11% → **12 条 3%**（合规率仅从 78% 降至 76%）

**权衡声明：** 这些规则偏向谨慎而非速度。对琐碎任务自行判断，对非平凡工作严格执行。

---

## 基础四原则（Karpathy 原始）

### 1. 编码前思考

**不要假设。不要隐藏困惑。呈现权衡。**

实现之前：
- 明确陈述你的假设。如果不确定，直接提问
- 如果存在多种解释，逐一呈现 — 不要默默选一个
- 如果有更简单的方案，说出来。必要时提出异议
- 如果某事不清楚，停下来。说出困惑之处。提问

### 2. 简洁优先

**用最少代码解决问题。不做推测性功能。**

- 不添加需求之外的功能
- 不为一次性代码创建抽象
- 不添加未被要求的「灵活性」或「可配置性」
- 不为不可能发生的场景做错误处理
- 如果 200 行可以写成 50 行，重写它

自问：「高级工程师会觉得这过于复杂吗？」如果会，简化。

### 3. 精准修改

**只碰必须碰的。只清理自己造成的混乱。**

编辑已有代码时：
- 不要「顺手改进」相邻代码、注释或格式
- 不要重构没坏的东西
- 匹配现有风格，即使你更倾向不同的写法
- 发现无关的死代码 → 提一下，不要擅自删除

当你的修改造成孤儿代码时：
- 删除因你的修改而不再使用的 import / 变量 / 函数
- 不要删除之前就存在的死代码（除非明确要求）

**检验标准：** 每一行修改都能直接追溯到用户的请求。

### 4. 目标驱动执行

**定义成功标准。循环验证直到达成。**

将指令式任务转化为可验证目标：
- 「加验证」→「为非法输入写测试，然后让它们通过」
- 「修 bug」→「写一个能复现的测试，然后让它通过」
- 「重构 X」→「确保重构前后测试都通过」

多步骤任务给出简短计划：
```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```

强成功标准让模型能独立循环执行。弱标准（「把它弄好」）需要不断澄清。

## Agent 时代扩展八条（@Mnilax）

### 5. 模型只做判断类任务

**分类、起草、摘要、提取 → 用模型。确定性逻辑 → 用代码。**

不要把 LLM 当作确定性执行引擎：
- 路由、重试、状态码判断、字符串处理 → 写普通代码
- 让模型专注于它擅长的：理解和生成
- 不确定性和判断 → 模型；确定性规则 → 代码

### 6. Token 预算是硬约束

**单任务 ≤ 4000 token，单会话 ≤ 30000 token。**

- 接近上限时主动总结并重置上下文
- 不要静默超出预算 — 超出的 token 意味着丢失上下文
- 长任务分段执行，每段结束后检查 token 消耗

### 7. 暴露冲突，不要折中

**代码库里两个模式冲突时，选一个，不要混搭。**

- 遇到冲突的代码模式，选择更新/测试更充分的那个
- 明确说明为什么选它，标记另一个为待统一
- 禁止「各取一半」的折中方案 — 那会产生第三种没人理解的模式

### 8. 写之前先读

**理解 exports、调用方、共享工具函数，然后再动手。**

- 「看起来不相关」是最危险的判断
- 新代码加入前，先读它即将调用的函数签名和实现
- 先读被修改文件的 imports 和邻近代码，理解数据流

### 9. 测试验证意图，而非行为

**测试必须随业务逻辑变更而失败，否则只是虚假安全感。**

- 好的测试编码了「为什么这个行为重要」
- 坏的测试只验证「返回值是什么」，业务逻辑变了测试照样通过
- 写测试时问自己：如果需求变了，这个测试会失败吗？不会 → 重写

### 10. 多步骤任务步步检查点

**每完成一步：总结做了什么、验证了什么、还剩什么。**

- 没有清晰的检查点，不要继续下一步
- 格式：`[已完成] X → [已验证] Y → [剩余] Z`
- 这是对抗任务漂移的最有效手段

### 11. 遵循既有惯例

**snake_case 项目就写 snake_case，class component 项目就写 class component。**

- 代码库内的风格一致性 > 个人偏好
- 不同意现有风格 → 单独讨论，绝不单方面分叉
- 命名、文件结构、错误处理模式 → 全部对齐

### 12. 失败要显眼

**静默失败不可接受。不确定性必须暴露。**

- 「迁移完成」这句话如果跳过了 30 条记录，就是一句谎言
- 任何 filter 跳过数据 → 必须计数并报告
- 默认暴露不确定，而非隐藏它
- 部分成功 ≠ 成功，必须明确区分

## 关键禁令

| 不要 | 原因 |
|------|------|
| 规则超过 14 条 | 合规率从 76% 暴跌至 52% |
| 超过 ~200 行 | Anthropic 文档记载的有效上限 |
| 用例子代替规则 | 3 个例子的 token 成本 = 10 条规则；模型还会过拟合 |
| 模糊指令（「小心点」） | 仅 ~30% 合规率，且无法验证 |
| 角色扮演提示（「像高级工程师一样」） | 无效；规则式指令才有效 |
| 引用特定工具（「用 eslint」） | 工具没装就静默失败 |

## 如何判断规则在起作用

- diff 中不必要的改动显著减少 — 只出现被请求的改动
- 因过度复杂导致的重写显著减少 — 代码第一次就写得简洁
- 澄清问题在实现之前提出，而非在犯错之后
- 干净、精简的 PR — 没有顺手重构或「改进」
